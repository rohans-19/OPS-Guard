1. Project Overview
1.1 Problem Statement
Autonomous AI agents can inspect logs, diagnose application failures, query databases, execute commands,
and manage cloud infrastructure through tools. This creates security risks when malicious user prompts or
instructions embedded in untrusted operational data manipulate an agent into accessing protected
information or performing unauthorized actions.
OpsGuard-Bench proposes a reproducible local cloud simulation, an autonomous LLM-based
cloud-management agent, controlled attack scenarios, two security layers, restricted execution, and a
benchmark that measures security and legitimate task performance.
1.2 Proposed Solution
• Layer 1 — NLP-Based Prompt Security Middleware: inspects incoming prompts and untrusted operational
content; classifies or scores suspicious text; flags, quarantines, safely transforms, or blocks content according
to policy.
• Layer 2 — Independent Action-Level Security Guard: validates every proposed tool call against identity,
permissions, resource access, argument constraints, data-sensitivity rules, and operation-specific policies.
• Sensitive-data protection: filters tool responses and final outputs to prevent unauthorized disclosure.
• Restricted execution: uses least-privilege Kubernetes permissions and a controlled tool gateway.
• Benchmarking: compares baseline, NLP-only, guard-only, and combined configurations.
1.3 Research Questions
• Does combining prompt inspection and independent action enforcement reduce successful attacks and
sensitive-data disclosure while preserving legitimate task completion?
• How effective is NLP detection against direct and indirect prompt injection?
• How effectively does action-level enforcement block attacks when the NLP detector misses them?
• What trade-offs occur among security, utility, false blocking, and latency?
• How well does the detector generalize to attack patterns excluded from training?
Research novelty must be established through a literature review; these questions are not, by
themselves, proof of novelty.
2. Scope and Boundaries
2.1 Required Features
• Reproducible local cloud simulation.
• Autonomous agent with a controlled tool interface.
• Direct malicious-prompt and indirect prompt-injection simulation.
• NLP middleware and independent action-level guard.
• Restricted execution, sensitive-data protection, and audit logs.
• Automated benchmark runner and four-configuration comparison.
• Quantitative metrics, visualizations, tests, and reproducible documentation.
2.2 Excluded from the Initial Version
• Production cloud deployment, real customer data, or real credentials.
• Reinforcement learning or DQN-based remediation.
• Federated learning or a multi-agent architecture.

5. Detailed Implementation Pipeline
Phase 1 — Repository and Environment
• Initialize Git, Python environment, dependency management, configuration, structured logging, health
endpoint, and test setup.
• Keep secrets out of source control; provide an .env.example with placeholders.
• Acceptance: backend starts, configuration loads, tests run, and setup instructions work from a clean
environment.
Phase 2 — Local Cloud Simulation
• Create a kind cluster; deploy a sample application and simulated database.
• Populate synthetic records and dummy sensitive values; generate logs, alerts, events, runbooks, and
reproducible failures.
• Create a dedicated ServiceAccount and least-privilege RBAC rules.
• Acceptance: environment can be reset, approved data is accessible through tools, and platform permissions
deny unauthorized access.
Phase 3 — Autonomous Agent
• Use LangGraph or a similar orchestration workflow with a provider-neutral LLM adapter.
• Workflow: receive task → inspect approved resources → retrieve operational data → diagnose → propose
action → submit to guard → execute if authorized → verify → respond.
• Register only explicit tools: get_application_status, get_pod_status, read_application_logs,
get_resource_metadata, restart_approved_application, query_approved_demo_records, and a restricted
access-test tool.
• Acceptance: legitimate tasks work, schemas are validated, and no direct path bypasses the execution
gateway.
Phase 4 — Attack Simulation
• Direct attacks: unauthorized credential retrieval, protected-resource deletion, permission escalation,
policy-bypass requests, and restricted-record access.
• Indirect attacks: instructions embedded in logs, alerts, Kubernetes events, runbooks, and incident reports.
• Benign controls: normal errors, security terminology used harmlessly, legitimate troubleshooting, and
authorized restarts.
• Mixed cases: useful evidence plus malicious text, or a legitimate request with an unauthorized secondary
action.
• Create a hand-labeled seed set and expand to approximately 500–1,000 scenarios if feasible; this is a starting
target, not proof of statistical sufficiency.
• Keep related templates and near-duplicates in the same split to reduce train/test leakage.
Phase 5 — Layer 1 NLP Middleware
• Baseline: TF-IDF + Logistic Regression; tune threshold on validation data.
• Optional comparison: fine-tune a compatible Hugging Face text classifier if resources permit.
• Inspect user prompts and untrusted text with provenance metadata; return label, risk score, model version,
decision, source type, and latency.
• Keep classification separate from handling policy. Do not treat the classifier as an authorization boundary.
• Acceptance: held-out precision, recall, F1, false-positive rate, and latency are reported; benign
security-related text is tested.

Phase 6 — Layer 2 Action Guard
• Validate identity, registered tool, schema, arguments, target resource, operation permissions, and
sensitive-data rules.
• Support ALLOW, DENY, and REVIEW; review must not automatically authorize execution.
• Default to deny when authorization cannot be established.
• Place all tool execution behind the guard and use least-privilege Kubernetes permissions.
• Filter tool responses and final output to prevent unauthorized sensitive-data disclosure.
• Acceptance: unknown tools, malformed arguments, unauthorized resources, and prohibited actions are
denied and audited.
Phase 7 — Integration
• Inspect the user task; retrieve data only through approved tools; inspect untrusted content before adding it
to agent context.
• Preserve provenance and distinguish evidence from instructions.
• Submit every proposed action to Layer 2; execute only after authorization.
• Filter tool output before it re-enters context and check final responses for prohibited disclosure.
• Test detector misses, malicious logs, benign security text, authorized restarts, secret requests, and
fail-closed behavior.
Phase 8 — Benchmark Runner
• Load scenario and configuration; reset environment; execute trial; collect events; evaluate attack objective
and disclosure; save metrics.
• Use identical scenarios, model settings, tools, environment, and evaluation rules across configurations.
• Repeat nondeterministic trials where practical and record trial counts.

9. Threat Model and Security Requirements
Protected Assets
• Synthetic credentials and restricted records.
• Kubernetes resources and application availability.
• Agent permissions and policy integrity.
• Audit records and experiment results.
Threat Actors
• A user attempting to exceed their authorization.
• An attacker supplying malicious text through a legitimate-looking request.
• An attacker who can influence operational content.
• A malicious or compromised data source embedding instructions in logs, alerts, or runbooks.
Security Goals
• Prevent unauthorized resource access and modification.
• Prevent protected-data disclosure.
• Prevent untrusted text from overriding trusted application policies.
• Prevent bypass of the tool execution gateway.
• Preserve legitimate troubleshooting utility.
• Produce auditable decisions and reproducible results.
Assumptions and Limitations
The initial environment is local and simulated, data is synthetic, and the LLM and NLP detector may fail.
Operational text is untrusted by default. The initial threat model does not cover a fully compromised host,
malicious kernel, or attacker who can alter the trusted guard configuration.
10. Key Engineering Principles
• Separate detection from enforcement.
• Use least privilege and default-deny behavior.
• Preserve source provenance and trust boundaries.
• Inspect inputs, tool responses, and final outputs.
• Avoid unrestricted shell tools.
• Use deterministic, reproducible evaluation rules.
• Measure security and legitimate utility together.

12. Definition of Project Completion
• Local simulation can be initialized and reset.
• Agent completes predefined legitimate tasks using registered tools.
• Direct and indirect attack scenarios are reproducible.
• NLP middleware inspects prompts and untrusted operational content.
• Action guard independently enforces permissions and security policies.
• Unauthorized actions are blocked before execution.
• Synthetic protected credentials cannot be disclosed through implemented interfaces to unauthorized
principals.
• Mandatory policy enforcement remains active when the NLP detector is disabled.
• All four benchmark configurations run on the same scenario set.
• Metrics are calculated and stored automatically.
• Tests and documentation enable another developer to reproduce experiments.
Functional completion does not establish research novelty or guarantee journal acceptance.
Those depend on the literature review, methodological rigor, experimental quality, and
demonstrated contribution.

Final Recommendation
Prioritize security enforcement and benchmark methodology before frontend development.
The central contribution to evaluate is whether NLP-based detection combined with
independent action-level enforcement improves attack resistance while preserving legitimate
cloud-management functionality.
Treat the benchmark as a research artifact: version its scenarios, document labeling rules, separate training
and test data, preserve reproducibility, report failures, and distinguish demonstrated results from
hypotheses.
